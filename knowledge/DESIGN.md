# 文件夹原生知识工作台：产品设计草案

讨论整理日期：2026-11-11

状态：需求与产品方向整理，不代表功能已经实现。本文记录当前共识、建议方案和待定问题，作为后续设计与开发的依据。

补充确认：应用形态为桌面应用，采用 VS Code 风格工作台，基于 Code - OSS 二次开发，而不是从零仿制界面。2026-11-11 已开始实现：固定 Code - OSS 1.145.3 源码基线，构建独立桌面开发版并集成内置知识扩展；当前能力与运行方式见 [桌面应用说明](../desktop/README.md)。本文其余内容仍是完整产品设计，不能视作已实现功能清单。

## 1. 背景与方向修正

Solutions 原本是一个文档与素材仓库，使用 MkDocs 发布静态站点。最初讨论的目标是把可解析的资料转化为知识，自动建立关联，帮助查找、理解和复用。

最早实现的实验版采用“导入资料到本地知识库，再搜索与查看图谱”的形态。后续讨论明确：这不是目标产品的主要使用方式。

目标不是让用户把资料搬进一个新的文档平台，而是直接围绕用户已经拥有的文件夹工作：

> 打开任意一个目录，理解其中的资料、资料之间的关系，以及它们随版本发生的演变。

现有实验版的使用与能力边界见 [README](./README.md)。本文描述的是后续产品方向；不应把实验版现状当成最终设计约束。

## 2. 已确认的核心需求

1. 工具可以打开任意一个用户选择的目录，而不是只处理本项目的文档目录。
2. 目录下各级子目录是知识聚合的基本单位。
3. 文件是知识来源的基本单位。
4. 知识来源不局限于 Markdown，还包括 Word、PPT、图片、draw.io 等流程图及其他可解析内容。
5. 工具不仅存放资料，还需要帮助用户组织、理解和更高效地使用资料；具体交互仍需继续设计。
6. 工具应理解 Git 修改历史，具备历史追踪和知识演变理解能力。
7. 产品是桌面应用，采用类似 VS Code 的编辑器工作台 UI，而不是以浏览器中的上传式资料库作为最终产品形态。

技术方向：以 Code - OSS 为桌面工作台基座，复用其成熟的目录、标签页、分栏、命令和扩展机制，把开发重点放在知识能力上。这里指开源源码，不是直接修改或重新分发微软品牌的 Visual Studio Code 发行版。

工作定位：

> 一个文件夹原生、证据驱动、能够理解版本演变的桌面知识工作台。

知识图谱是组织与解释关联的一种能力，不是唯一的数据表达方式，也不应成为必须经过的操作入口。

## 3. 核心概念

| 概念 | 含义 | 职责 |
| --- | --- | --- |
| 工作区 | 用户打开的根目录 | 确定读取边界，管理索引、处理状态和使用偏好 |
| 知识集合 | 根目录中的各级子目录 | 按目录聚合资料，形成主题与上下文 |
| 知识来源 | 一个原始文件 | 保持出处，支持预览、解析、引用和变化追踪 |
| 证据片段 | 来源中可定位的一部分内容 | 作为检索结果、断言和回答的引用依据 |
| 来源版本 | 文件在工作区或某次 Git 提交下的内容状态 | 明确知识依据的是哪个版本 |
| 知识断言 | 从来源提取出的带条件的关系或陈述 | 关联证据、适用范围、抽取方法和审核状态 |
| 知识卡片 | 用户保存的整理结果或判断 | 区分原始资料与用户理解，追踪依据是否变化 |

前四项构成基本层次：

```text
工作区
  └─ 知识集合（目录，可嵌套）
       └─ 知识来源（文件）
            └─ 来源版本
                 └─ 证据片段
```

工作区根目录也可能直接包含文件，不能遗漏；建议提供根级集合视图。集合默认聚合直属资料还是全部后代资料、如何切换范围，仍需明确交互。

文件在物理上属于所在目录，但可以被多个主题视图引用，不需要复制文件。

## 4. 文件管理原则

### 4.1 文件系统是基础，不要求资料搬家

建议采用“原文件保留，索引旁路保存”的方式：

- 用户选择目录后即可使用，不要求上传或复制到工具专有资料库。
- 目录结构是用户已有的组织成果，工具首先尊重它。
- Word、PowerPoint、draw.io 等原生软件仍负责编辑原文件。
- 默认只读，不擅自改名、移动、删除或重写文件。
- 索引、摘要、关系、人工备注等衍生数据独立保存。
- 工具停止使用或卸载后，原始资料仍能独立使用。
- 观察新增、修改、移动和删除，更新受影响的派生数据。

旁路数据的具体存放位置、便携模式、备份与同步方式尚未确定。

### 4.2 两种组织方式并存

**目录集合**忠实对应物理目录，是最基本的组织和范围选择方式。

**虚拟集合**按主题、标签、收藏或查询条件跨目录聚合，不改变原文件的位置。例如“审批流程”可以关联多个项目中的需求、会议记录和流程图。

优先实现目录集合；虚拟集合的类型、维护方式和上线阶段待定。

### 4.3 变化不能破坏来源关系

- 内容变化后，标记相关索引、摘要、断言和卡片需要重算或复核。
- 移动或重命名时，尽可能保留来源连续性，但不能把启发式匹配当成确定事实。
- 内容相同的两个文件仍可能拥有不同出处，不应只凭内容哈希就丢弃其中一个来源。
- 来源删除后的当前视图、历史视图和人工卡片应如何保留，需要分别制定规则。

## 5. 多格式理解：统一来源，不抹平结构

各种内容都可以统一视为“知识来源”，但不能全部压平成纯文本，否则会丢失关系、布局、单位和上下文。

| 格式 | 需要保留的结构 | 证据定位方式 |
| --- | --- | --- |
| Markdown、文本 | 标题、段落、链接、代码、附件关系 | 章节、行号或片段位置 |
| Word | 标题层级、段落、表格、嵌入图片 | 文档结构位置；可用时关联渲染位置 |
| PPT | 页序、文字、备注、图形与页面视觉 | 幻灯片及页内对象或区域 |
| 图片、扫描件 | 原图、OCR 文本、区域与视觉上下文 | 图片区域 |
| draw.io 等流程图 | 节点、连线、标签、分组、页面和布局 | 图页、节点或连线标识 |
| 表格资料 | 工作表、表头、行列、公式和单位 | 工作表与单元格区域 |
| 代码 | 符号、类型、调用、注释和运行环境 | 文件位置或符号 |
| 后续音视频 | 转写、时间戳、必要的说话人或关键帧 | 时间区间 |

Word、PPT 的支持范围应区分现代格式 `.docx/.pptx` 与旧格式 `.doc/.ppt`；后者可能依赖额外转换能力。上述表格是能力方向，不是首版全部支持的承诺。

对于 draw.io 等结构化图：

- 优先解析原生节点与连线，不先截图再让模型猜结构。
- 区分“原图明确表达的连接”与“模型推断的业务含义”。
- 只有截图时，识别出的图结构属于候选结果，保留不确定性。

解析失败或缺少转换器时，来源仍应可见，并说明失败原因、缺少的能力和可执行的下一步；不能伪装成解析成功。

## 6. 知识组织与可信性

### 6.1 不让所有内容都必须进入图谱

图谱适合表达实体与关系；长篇解释、代码、步骤、版面和完整上下文仍应保留在来源中。

全文检索、后续的语义检索、结构化关系和原文阅读互相补充。不能为了生成图谱而丢弃不适合三元组表达的信息。

### 6.2 明确区分关系类型

1. **组织关系**：文件属于哪个目录，目录包含哪些子集合。
2. **来源结构关系**：文档引用链接，流程图节点之间的明确连接等。
3. **语义断言**：资料表达的使用、依赖、解决、适用或替代关系等。
4. **推断与个人判断**：模型提出的关联或用户自己的整理结论。

共同出现不等于依赖，模型生成不等于事实验证。原作者的陈述也应作为“来源表达了什么”保存，而非自动升级为客观真理。

### 6.3 每条有用的结论都能回到证据

建议保留：

- 来源及其版本。
- 原文片段和结构位置。
- 适用条件、版本限制与时间范围。
- 生成方法及处理版本。
- 人工审核或修订状态。

精确引用只证明原文存在，不证明结论正确。模型自报置信度不能直接称作经过校准的正确率。

人工判断不应被重新解析覆盖；来源变化后应提示复核，而不是静默改写用户已经保存的结论。

### 6.4 衍生数据应可重建

原始资料与人工修订是长期资产。解析结果、索引、自动摘要和图谱是派生数据，应支持在更换解析器、抽取规则或模型后重新生成。

具体实体类型、关系词表、别名合并、同名消歧及冲突处理规则仍需设计，不直接把软件开发领域的关系类型推广到所有知识领域。

## 7. 主要使用场景

### 7.1 找到资料中的具体内容

问题示例：

> 哪份 PPT 讲过设备异常后的恢复流程？

结果应呈现相关页面或片段、文件位置与上下文，而不只是返回文件名。

### 7.2 理解一个文件夹

问题示例：

> 我要接手这个项目，目录里有哪些关键资料，应该按什么顺序看？

建议提供集合级概览、子主题、关键来源和有依据的阅读顺序，而不是机械拼接各文件摘要。

### 7.3 对照多个来源

问题示例：

> 需求文档和流程图对审批步骤的描述是否一致？

并排呈现相关段落、幻灯片或节点。模型可以提出差异候选，但证据必须可见，不能把差异自动解释成错误。

### 7.4 在明确范围内提问

问题示例：

> 仅根据这个项目目录，上线需要满足哪些条件？

建议当前选中的集合就是默认检索范围，界面显式显示该范围。跨集合查找或引入外部知识应主动说明，不能混入其他项目的内容而不提示。

### 7.5 沉淀知识卡片

卡片建议包含：

- 结论、导读或整理结果。
- 支持结论的来源、具体版本和片段。
- 适用范围与个人补充。
- 依据变化后的复核状态。

原文件记录“来源说过什么”，卡片记录“我目前如何理解它”。两者不能混淆。

## 8. 桌面工作台与交互形态

### 8.1 已确认的应用形态

产品是桌面应用，采用类似 VS Code 的编辑器工作台布局。用户打开本机目录，在同一个工作台中浏览集合、阅读多格式来源、查看证据与历史，并使用知识助手。

现有本地服务加浏览器的实验版只用于验证部分能力，不是最终客户端形态。后续以 Code - OSS 的 Electron 桌面工作台为基座，知识能力的进程划分、服务接口与数据存储仍需设计。

此处不再只是模仿 VS Code 的布局，而是复用其开源工作台。原格式编辑、多媒体编辑和完整 IDE 能力不因选用该基座而自动纳入首版范围；保留哪些开发者界面和命令需要按知识工作台的定位取舍。

### 8.2 建议的工作台分区

| 区域 | 建议职责 |
| --- | --- |
| 顶部标题栏与命令入口 | 当前工作区、打开文件夹、全局命令、搜索与当前范围 |
| 最左侧活动栏 | 切换资源管理器、搜索、知识视图与 Git 历史 |
| 左侧主侧栏 | 目录树、集合、检索结果或历史导航 |
| 中央多标签页区域 | 集合概览、原文预览、版本对照、知识卡片和局部图谱 |
| 右侧可收起辅助栏 | 知识助手、来源证据、相关资料与复核信息 |
| 底部可收起面板 | 解析任务、处理报告、错误与诊断 |
| 状态栏 | 当前集合与版本、索引状态、任务进度和模型连接状态 |

具体分区、默认显隐和快捷键属于建议，仍需通过原型验证。中央区域优先用于阅读和研究；默认入口建议是文件夹概览，而不是聊天框或全库关系大图。

```text
┌────────────────────────────────────────────────────────────────┐
│ 工作区名称          命令 / 搜索入口          当前范围与版本      │
├──────┬──────────────┬──────────────────────────┬────────────────┤
│活动栏│ 主侧栏        │ 中央标签页                │ 辅助栏          │
│      │              │ 概览 | 需求.docx | 对照    │                │
│ 文件 │ 项目 A       ├──────────────────────────┤ 助手与证据      │
│ 搜索 │ ├─需求       │ 集合概览 / 来源预览       │ 范围内查找      │
│ 知识 │ ├─设计       │ 原文 / 证据 / 演变        │ 对照多份来源    │
│ 历史 │ └─会议       │                          │ 回答及引用      │
│      │              │                          │ 保存知识卡片    │
│      │ 收藏 / 主题   ├──────────────────────────┴────────────────┤
│      │              │ 底部面板：解析任务 / 报告 / 诊断           │
├──────┴──────────────┴───────────────────────────────────────────┤
│ 索引与任务状态         当前集合 / Git 版本         模型状态      │
└────────────────────────────────────────────────────────────────┘
```

### 8.3 集合与来源的呈现

集合视图建议展示：

- 目录内容概览与子主题。
- 关键文件及其作用。
- 解析成功、待处理、失败和发生变化的状态。
- 文件之间明确的引用，以及需要人工核验的关联或差异。
- 用户对目录用途、背景与适用范围的说明。

AI 概览需注明依据和更新时间。“最近修改”不能自动等同于“最权威”或“最终版本”。

图谱作为局部关联视图按需出现；不优先构建一次展开全库节点的大图。桌面应用与 VS Code 风格工作台已确认，上述具体面板职责、阅读布局和交互细节仍属于建议。

建议支持多标签阅读、来源并排对照、面板显隐切换，以及通过桌面文件夹选择器打开目录。是否支持分栏拖拽、会话恢复、多窗口和完整命令面板，仍需确定首版范围。

### 8.4 基于 Code - OSS 二次开发

#### 选择依据

Code - OSS 是 `microsoft/vscode` 仓库中的开源编辑器项目，源码采用 MIT 许可证。微软品牌的 Visual Studio Code 是在此基础上加入定制后发布的发行版，适用不同的产品许可。

基于 Code - OSS 可以复用：

- 桌面窗口、工作区、文件资源管理器和文件变化通知能力。
- 标签页、分栏、面板、命令、快捷键、设置和主题。
- 扩展宿主、树视图、Webview 与自定义编辑器等扩展机制。
- 既有的 Git 和差异展示能力，作为历史功能的部分基础。

复用工作台不等于获得知识能力。目录语义聚合、Word/PPT 结构解析、图片理解、draw.io 语义、跨来源证据、知识卡片和历史知识推理仍需自行实现。既有 Git UI 也不能直接替代历史知识引擎。

#### 建议的定制边界

```text
自有品牌的桌面应用
  └─ Code - OSS 工作台
       ├─ 复用：目录、工作区、标签页、分栏、命令与设置
       ├─ 内置知识扩展：集合概览、阅读器、助手、证据与演变视图
       └─ 知识引擎：解析、索引、来源版本、模型调用与 Git 历史分析
```

建议尽量用自有内置扩展承载知识功能，通过树视图、自定义编辑器和 Webview 接入；只在扩展机制无法满足产品体验时修改工作台核心。目标仍是独立桌面产品，而非仅要求用户安装到现有 VS Code 的插件；但可以先用扩展原型验证交互与接口。

解析、索引与模型任务不得阻塞工作台 UI。重型或不可信格式解析应考虑独立进程与资源限制；具体隔离和通信方案需要验证。

现有实验版仅作可复用能力候选。尤其需要核对目标 Code - OSS 内嵌的 Node/Electron、扩展宿主和数据库 API；不能假设当前依赖 Node.js 24 内置 SQLite 的实现可以不经适配直接嵌入。

#### 发行与维护边界

- 使用自有应用名称、图标、应用标识、数据目录和发行配置，不沿用微软品牌身份。
- 保留 Code - OSS 及其他依赖要求的许可证和版权声明；分别明确新增代码、现有内容和第三方扩展的许可。
- 开源源码许可不自动授予 Visual Studio Marketplace、微软专有服务或品牌资源的使用权。不得简单复制微软发行版的服务配置。
- 不默认假设所有 VS Code 扩展都可以在自有发行版中使用或随应用打包，需逐项核对扩展许可、兼容性及其依赖服务。是否使用 Open VSX 或自有分发方式另行评估。
- 确定可复现的上游版本基线、补丁管理方式和升级节奏；持续跟进 Code - OSS、Electron 和 Chromium 的安全修复。
- 自行规划签名、安装包、更新、崩溃报告与遥测策略，不把上游发行服务视为可直接继承的能力。
- 基座源码规模、构建资源和持续合并成本明显高于一个小型独立壳应用，应纳入实施评估。

当前已按固定源码基线、独立产品配置和小范围补丁构建桌面开发版，并通过内置扩展接入基础知识能力。正式发行、签名、自动更新、上游升级与完整知识引擎仍需继续完善；实现边界见 [桌面应用说明](../desktop/README.md)。

## 9. Git 与历史理解

### 9.1 Git 是知识时间维度，不只是提交列表

工具不仅要理解资料现在表达什么，还要理解：

> 在某个版本下，某个集合中有哪些来源，它们表达了什么，后来又发生了什么变化。

历史能力分三层：

| 层次 | 需要回答的问题 |
| --- | --- |
| 文件历史 | 何时增加、修改、移动、删除了哪些文件？ |
| 内容变化 | 具体改变了哪些段落、表格、幻灯片或流程节点？ |
| 知识演变 | 哪个方案被替代，哪个条件被收紧，某个结论从什么时候开始改变？ |

变化解释示例：

> 这一版增加了人工复核步骤，同时需求文档新增了对应限制；更早版本没有这项要求。

事实变化与变化原因必须区分。提交说明或正文没有明确解释原因时，不得编造“为什么改”。

### 9.2 历史使用场景

- 按文件或集合查看变更时间线。
- 选择两个版本，并排查看原始差异与知识变化。
- 回到某次提交回答“当时的部署要求是什么”。
- 追问“这个方案从什么时候开始不再推荐”。
- 来源变化后，定位受影响的摘要、断言和知识卡片。

历史引用应绑定具体提交、路径、文件内容版本和证据位置，而不是仅保存一个可能继续变化的当前路径。

提交时间不一定是知识生效时间；提交说明也不是完整的变更动机。历史回答要说明其可证实的范围。

### 9.3 非文本文件的历史

Git 对 Word、PPT、图片等文件通常只能给出二进制内容变化。工具需要读取前后版本，再基于对应解析器比较：

- Word 的段落、标题、表格。
- PPT 的页面、文字、备注和布局。
- draw.io 的节点、连线、标签与分组。
- 图片的视觉变化及识别结果。

职责分工：

> Git 提供版本证据，解析器提供内容结构，模型辅助解释变化。

不同格式的对象匹配和语义差异可能不可靠，应保留不确定性，并允许回看两个版本的原始资料。

### 9.4 仓库边界与只读原则

- Git 不是使用前提；普通目录仍能工作。
- 检测到仓库后开启历史能力。非 Git 目录的本地快照是可选方向，不能宣称 Git 能提供其过去历史。
- 工作区未提交修改与已提交版本必须分开，不能互相冒充。
- 分支与合并构成图，不是一条简单时间线。历史查询需要明确分支或提交。
- 默认沿当前分支查看、按需展开合并关系是建议方案，具体遍历规则待定。
- 打开仓库中的子目录时，不能因为发现仓库根目录就默认扩大内容读取范围。
- 嵌套仓库、子模块、Git LFS、浅克隆和缺失对象需要单独说明支持边界。
- 不切换用户分支，不改写工作区，不自动提交，不执行仓库脚本，不自动拉取远端。
- 重命名、复制、拆分、合并的来源关联必须保留依据，无法确认时不强行认作同一来源。

### 9.5 历史隐私

删除当前文件不代表 Git 历史中已没有这份内容。历史中也可能存在不再适合读取或发送给模型的资料。

因此历史索引需要明确授权范围、排除规则和清理能力。不能默认对完整仓库历史做全量模型分析，也不能认为当前忽略规则天然等于历史访问策略。

### 9.6 按需处理，避免全历史重复计算

建议：

1. 先识别仓库与范围，读取必要的提交和文件变更元数据。
2. 默认索引当前资料，历史正文按需解析。
3. 按文件内容版本复用解析结果，同时保留不同路径与提交的来源关系。
4. 用户选择文件、集合或版本区间后，再生成有证据的变化解释。
5. 解析器或模型变化时，对缓存结果做版本管理，避免复用过期处理结果。

## 10. 隐私、可靠性与失败处理

- 用户明确选择的目录是读取边界，不默认递归读取外部链接目标。
- 私有目录、隐藏目录、忽略规则与排除规则应可理解、可检查；不把固定目录名排除当作完整隐私保障。
- 不自动上传资料。是否支持远程模型、如何授权、发送范围如何提示，尚未确定。
- 解析器只读取资料，不执行来源中的代码、脚本或指令。
- 图片识别、OCR、模型抽取和原生格式解析具有不同可靠性，应区分展示。
- 每份文件都有可见处理状态；失败要报告原因，允许重试，不用空摘要掩盖失败。
- 设定文件大小、解压规模、处理时间和模型输出限制；具体阈值按格式与实际资料验证后确定。
- 数据备份、工作区移除、索引清理和历史内容保留需要有明确规则。
- 原有内容授权不能因导入而改变；代码与内容许可、公开导出和第三方资料再分发需分别考虑。

## 11. 建议的实施路线

### 阶段一：工作区与来源基础

- 打开任意用户选择目录，展示完整目录与文件层次。
- 选定并验证 Code - OSS 上游构建基线，确定自有发行配置与最小核心定制边界。
- 通过内置知识扩展和必要的工作台定制，组织目录、中央阅读区、辅助面板与状态信息。
- 明确集合范围、来源身份、旁路存储和处理状态。
- 保持原文件不动，支持变化发现与索引更新。
- 同时建立版本与证据模型，检测 Git 仓库边界，区分当前修改与提交状态。

### 阶段二：多格式阅读与定位

- 用代表性的 Markdown、DOCX、PPTX、图片和 draw.io 样本验证解析能力。
- 保留结构及原始阅读入口，打通检索结果到来源片段的定位。
- 增加选定 Git 版本的按需读取与解析，不自动解析全部历史。
- 明确旧格式、复杂嵌入对象和无法解析文件的处理方式。

### 阶段三：集合级检索与导读

- 按文件夹和版本限定检索范围。
- 提供有引用的目录概览、主题与阅读顺序。
- 验证是否真正帮助找到资料和理解集合。

### 阶段四：跨来源研究与历史理解

- 带引用的问答、多来源对照。
- 版本对照、知识变化解释与历史提问。
- 明确差异、冲突、版本适用范围和不确定性。

### 阶段五：知识沉淀与关联

- 知识卡片、人工审核与复核提醒。
- 跨目录虚拟集合和局部关联视图。
- 对实体消歧、别名和复杂历史匹配逐步完善。

阶段划分是讨论建议，不是排期承诺。Git 的数据与证据模型从基础阶段考虑，而不是在静态知识库完成后再补历史。

现有实验版中的来源追踪、检索、证据校验等代码可评估复用，但上传式交互、固定文档目录和当前数据模型需要调整。Code - OSS 已作为桌面基座方向，不由实验版的浏览器架构反向约束产品；知识引擎、解析器和模型服务的具体技术方案仍待验证。

## 12. 验证标准

不以生成了多少摘要、节点或连线衡量成功。需要用真实代表性资料验证：

1. 打开目录后，文件结构与原始资料保持完整，工具不造成隐式修改。
2. 文件夹范围内的问题能找到正确来源，不悄悄混入其他集合或版本。
3. Word、PPT、图片、流程图中的证据能回到对应位置。
4. 原始连接、模型推断和人工判断能清楚区分。
5. 文件修改、移动和删除后，相关索引与知识状态正确更新。
6. 历史回答依据指定版本，而非不小心使用当前正文。
7. 变更解释能回到前后版本证据，不编造变更动机。
8. 人工卡片与修订不会被自动重算覆盖，依据变化时能提示复核。
9. 解析失败、缺失历史对象、未支持格式与权限边界都可见。
10. 成本、延迟、资源占用和准确性以样本测量，不能只凭演示判断。

具体准确率、耗时、资料规模及支持格式的验收阈值，需要在选定样本和首版范围后制定。

## 13. 待定问题

- 选择哪个 Code - OSS 上游版本，如何管理 fork、补丁、依赖与持续升级？
- 内置知识扩展与工作台核心的修改边界是什么，知识引擎采用何种进程与通信方案？
- 首批支持哪些操作系统，如何构建、签名、打包和更新？
- 产品名称、品牌、扩展来源、服务配置与新增代码许可如何确定？
- VS Code 风格工作台中，哪些面板、标签页、分栏、命令和快捷键进入首版？
- 打开目录、切换工作区与保存工作区状态如何交互？
- 集合范围如何表达直属文件与递归后代，如何处理跨目录引用？
- 首版格式支持顺序，Word/PPT 旧格式与复杂对象支持到什么程度？
- 是否提供完整原格式渲染，还是先提供结构预览与原生软件跳转？
- 本地模型与远程模型的支持策略、权限提示与成本控制是什么？
- 全文检索、语义检索、结构检索如何组合？
- 旁路数据放在哪里，是否支持便携、同步与多设备？
- 来源身份如何应对移动、复制、重命名、拆分与合并？
- 如何选择历史范围，如何呈现分支与合并？
- 非 Git 目录是否需要本地快照，何时启用及如何限制空间占用？
- 知识卡片如何编辑、导出、分享与追踪依据变化？
- 哪些派生结果可以自动更新，哪些必须等待人工确认？

下一步应先确定首版用户流程、代表性资料样本和验收范围，再按此调整架构与实现，避免继续沿上传式资料库的方向堆叠功能。
